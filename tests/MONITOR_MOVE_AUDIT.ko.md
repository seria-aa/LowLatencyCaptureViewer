# 모니터 이동 / DPI 이벤트 가상 검증 (2026-09-11)

## 범위
- 실제 main.cpp의 WndProc, ApplyRelativeSizeForMonitor, DPI 처리 및 OutputTransitionState를 실행.
- 테스트 번역 단위에서만 Win32 모니터 조회, 커서, 창 위치/크기 API를 가짜 구현으로 연결.
- 1920×1080 / 2560×1440, 96/144 DPI, 우측/좌측/상단 배치, 상대 크기 켬/끔, DPI/이동 순서 2종: 24조건 × 100회 = 2,400회.
- 창은 non-client 여백이 없는 가상 borderless 창. 실제 창, GPU, 오디오/캡처 하드웨어는 열지 않는다.
- Windows 메시지 순서를 테스트가 공급한다. 실제 OS에서 각 순서가 발생한다는 증명, DWM/MPO/Independent Flip, DP/HDMI 링크 또는 검은 화면 재현이 아니다.
- CTest 성공은 아래 관찰한 현재 동작과 안정화 조건을 검증했다는 뜻이며, 아래 취약점이 수정됐다는 뜻이 아니다.

## 결과
1. 서로 해상도가 다른 모니터로 상대 크기 이동:
   - 경계 1회 통과: 이동 중 출력 generation 증가 1회.
   - 경계 100회 왕복: 이동 중 generation 증가 100회, 이동 종료 추가 증가 0회.
   - 대조: 수동 크기 변경 100회는 이동 중 증가 0회, 종료 후 1회.
   - 원인: WM_SIZING만 manualResize를 설정한다. WM_MOVING의 자동 크기 변경은 그 유예 대상이 아니다.
   - generation은 **재생성 요청**이다. 렌더 스레드가 여러 변경을 한 번에 관측하면 합쳐질 수 있으므로 GPU 재생성 100회를 측정한 결과는 아니다.
   - 렌더 루프는 generation 변경을 관측하면 renderer.initialize를 호출하며, initialize는 reset 후 장치와 스왑체인을 재구성한다. 따라서 이동 중 연속 재생성 가능성은 코드와 연결된다.

2. DPI 사전 계산과 상대 크기 이동의 대상 모니터 불일치:
   - WM_GETDPISCALEDSIZE는 커서가 있는 모니터로 목표 크기를 계산한다.
   - 두 번째 모니터로 이동 처리 후, 커서는 첫 번째 모니터에 있고 DPI 변경 대상은 두 번째 모니터인 순서를 주입.
   - 목표 폭 1280에서 첫 번째 모니터 기준 960으로 바뀌고, 커서를 두 번째 모니터로 다시 옮겨도 폭 960 유지. 재생성 요청 2회.
   - 상대 크기 이동의 캐시(g_relativeMoveMonitor)는 이미 두 번째 모니터이므로 재계산을 생략. 상대 크기 켬 상태의 NormalizeWindowSize도 바로 반환.
   - 이는 입력된 순서에 대한 정책 불일치 재현이다. 제보 환경에서 동일 순서가 발생했는지는 확인하지 못했다.

3. 안정화/대조 결과:
   - 같은 대상 모니터로 WM_MOVING 1,000회 반복 시 첫 변경 외 추가 재생성 요청 없음.
   - 상대 크기/Pixel-perfect 모두 끈 상태: 순수 이동 100회에 재생성 요청 없음.
   - 2,400회 시퀀스에서 유효한 크기, 종료 후 남은 transition 없음.
   - 시퀀스마다 동일 크기 알림 20회 추가 시 재생성 반복 없음.
   - 따라서 정지한 창에서 2분마다 신호가 끊기는 현상을 이 경로만으로 설명하거나 증명하지 못했다.
   - 캡처 장치 고주사율 목록 소실도 이번 테스트와 연결되지 않는다.
