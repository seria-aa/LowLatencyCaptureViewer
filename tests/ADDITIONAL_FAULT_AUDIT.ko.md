# 추가 가상 검증 — 2026-09-11

이 문서는 수정 전 감사 기록이다. 이후 보완과 현재 상태는
[FAULT_FIX_AND_MODULE_REVIEW.ko.md](FAULT_FIX_AND_MODULE_REVIEW.ko.md)를 참고한다.

## 결론

일반 회귀 테스트는 통과했지만, 새 실패 조건 검사에서 추가 보완점을 찾았다.
이번 작업은 **테스트와 기록만 추가**했으며 앱 소스, 설정, 릴리스 파일은 변경하지 않았다.
모니터 전체가 꺼지며 ‘신호 없음’이 표시되는 실제 문제를 재현하거나 원인을 확정한 것은 아니다.

## 발견한 조건

### 1. 잘못된 우선 후보가 정상 대체 후보까지 막음 — 우선 보완

모의 장치가 NV12 1080p120의 영상 크기를 1바이트라고 잘못 보고하고,
1080p60은 정상 보고하도록 했다. 장치는 두 모드의 SetFormat을 허용한다.

`ConfigureVideoPin`은 120fps의 SetFormat 성공 직후 후보 탐색을 끝내고,
그 뒤 크기 검증에서 `0x8007000D`로 종료한다. 정상 60fps 후보는 시도하지 않는다.
출력 버퍼를 잘못 사용하지 않고 중단하는 점은 안전하지만, 시작할 수 있는 대체 경로를 놓친다.
후보별 검증을 선택 과정 안에 넣고, 잘못된 후보를 건너뛰는 방식이 적절하다.

### 2. 기본 프레임 시간이 없으면 별도의 유효한 범위도 무시함 — 호환성 보완

AvgTimePerFrame=0, Min/MaxFrameInterval=41667/166667(약 60~240fps)인
모의 응답에서 목록이 비고, 요청한 120fps의 SetFormat도 시도하지 않는다.
실제 연결 이후 시간 정보 생략을 허용한 것과 달리, 목록 조회/초기 선택 단계에는
양수 기본 프레임 시간이 필수인 조건이 남아 있다.

이는 완전한 표준 응답의 보장이 아니라 일부 정보가 빠진 응답에 대한 복원력 문제다.
별도로 보고된 범위에서 요청값을 구성하고 실제 SetFormat 성공 여부로 판단할 수 있다.
Microsoft는 지원 프레임 범위 확인에 MinFrameInterval/MaxFrameInterval을 사용할 수 있다고
[명시한다](https://learn.microsoft.com/en-us/windows/win32/api/strmif/ns-strmif-video_stream_config_caps).
이 모의 응답을 GC573에서 실제 관측한 것은 아니다.

### 3. API 실패가 아닌 잘못된 내용은 조회 오류로 표시되지 않음 — 진단 보완

- 알려진 NV12 타입인데 형식 데이터가 비어 있는 경우: 조회 결과 S_OK, 빈 목록.
  현재 UI는 ‘조회 실패’가 아니라 ‘지원 모드 없음’ 경로를 탄다.
- NV12 1080p인데 영상 크기가 1바이트인 경우: 조회 결과 S_OK, 정상 항목처럼 목록에 남음.
  시작 단계에서야 형식 검증에 실패한다.

앞서 HRESULT 실패를 구분한 보완은 정상 작동한다. 이번 발견은 **성공으로 반환됐지만
내용이 잘못된 응답**까지 구분하지 못하는 별도 경계다. 정상적인 미지원 픽셀 포맷과
잘못된 지원 포맷을 구분해야 한다.

### 4. 출력 전환 중 크기 조절 종료 알림이 끼어들면 중복 재생성 요청 — 조건부 보완

실제 전환 함수와 창 메시지 처리기에 다음 순서를 주입했다.

1. BeginOutputTransition
2. 수동 크기 조절 중 상태와 WM_SIZE
3. 전환이 끝나기 전 WM_EXITSIZEMOVE
4. EndOutputTransition(true)

결과: 3번에서 이미 출력 세대가 한 번 증가하고, 4번에서 다시 증가한다.
WM_EXITSIZEMOVE의 보류 해제는 현재 전환 깊이를 확인하지 않는다.
전환 완료 전에는 보류를 유지하도록 일관성을 맞추는 것이 좋다.

일반적인 전환 순서 10,000개에서는 발견되지 않았다. 이 메시지 순서를 실제 사용자
PC에서 관측한 것은 아니며, 두 번의 요청이 반드시 두 번의 GPU 재생성으로 이어지는
것도 아니다. 렌더 스레드가 중간 상태를 볼 때만 실제 중간 재생성이 가능하다.
[WM_EXITSIZEMOVE는 이동/크기 조절 루프가 끝날 때의 알림](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-exitsizemove)이지만,
그것이 앱의 모든 출력 전환이 끝났다는 뜻인지는 별도로 관리해야 한다.

### 5. GetFormat의 성공+null 응답이 그대로 반환됨 — 낮은 우선순위 진단 방어

모의 장치가 GetFormat에서 S_OK와 null을 반환하면 `GetActiveVideoPinFormat`도
그대로 성공을 반환한다. 상위 캡처 루프는 null을 확인하고 종료하며, 최종 오류를
E_FAIL로 변환한다. 따라서 이것을 null 역참조나 조용한 성공으로 판정하지 않았다.
함수 경계에서 더 구체적으로 실패 처리하면 원인 추적이 쉬워진다.

[정상 GetFormat 계약](https://learn.microsoft.com/en-us/windows/win32/api/strmif/nf-strmif-iamstreamconfig-getformat)은
형식 구조체를 할당해서 반환하는 것이므로, 이 검사는 계약을 어긴 드라이버에 대한 방어 검사다.

## 통과한 추가 검사

- 영상 정보: 4개 난수 시드, NV12/YUY2/P010/MJPEG, 정상/비정상 정보 **20,000쌍**.
  다양한 크기·상하 방향·행 패딩, 짧은 형식 구조체, null, 부호 경계, 음수 시간 등을 포함.
  검증 실패 때 이전 출력값을 보존하는지도 확인했다. 실제 MJPEG 디코딩/HDR 재생 검사는 아니다.
- 프레임 전달: 8개 시드, **160,000건**. 음수·빈·짧은 샘플, 생산/소비 속도 차이,
  이벤트 대기와 즉시 읽기 교차, 중간 동시 진행 확인, 마지막 프레임 회수.
  소비/최신 프레임 교체/거부 수를 대조하고 모의 COM 샘플이 모두 해제됨을 확인했다.
- 출력 전환: 최대 4중 중첩, 중복/변경/최소화 알림, 수동 드래그, 명시적 출력 갱신을
  조합한 **10,000개 일반 순서**에서 보류 및 한 번 갱신 원칙을 확인했다.
- 위 세 검사를 각각 **10회 추가 반복**: 총 20만 정보 쌍, 160만 프레임 제출,
  10만 전환 순서 모두 통과. 같은 시드를 재사용하므로 서로 다른 하드웨어 실험 수가 아니다.
- Shared 오디오: 25ms 목표, 12개 새 시드, 2.667/3/4/5/8/10ms 출력 주기,
  4/8ms 도착 지터, 클록 방향 변화/완만한 변화, 입력 40ms·출력 20ms 동시 중단,
  입력 폐기/늦은 묶음 전달 조합. **30회 실행, 28개 서로 다른 조합**, 합산 가상 시간 96분.
  지터·클록 변화만 있는 경우 누락 0. 강제 중단 때 누락은 있었지만 진단 계산,
  목표 버퍼 유지, 보정 범위, 복구 완료 검사는 모두 통과했다.
  이는 실제 기기의 96분 연속 사용 검증이 아니다.
- 로컬 RTX 3080 D3D11 debug: NV12/YUY2 × 저지연/VSync/Blt × 120프레임,
  **720프레임**, 경고/오류 0. 숨긴 창이라 모든 Present가 occluded였으며
  모니터 신호·MPO·표시 지연은 검사하지 못한다.
- 기본 CTest **15/15 통과**, 96.21초. 이 결과는 위의 새 결함 검사까지 통과했다는 뜻이 아니다.

## 실패 검사 실행법과 한계

새 검사들은 별도 실행 옵션이다. 결함 탐지용 두 옵션은 현재 의도한 안전 조건과
실제 구현의 차이를 드러내도록 **실패 코드를 반환**하며, 통과로 둔갑시키지 않았다.

```powershell
./build-v1261-test/DirectShowVideoFormatTests.exe --faults
# exit 1: 위 1/2/3/5의 기대 조건 여섯 개 실패
./build-v1261-test/AudioCallbackTests.exe --transition-faults
# exit 1: 위 4의 조기/중복 갱신 조건 두 개 실패

./build-v1261-test/DirectShowVideoFormatTests.exe --stress
./build-v1261-test/LatestVideoSampleTests.exe --stress
./build-v1261-test/AudioCallbackTests.exe --transition-stress
./build-v1261-test/SharedReplayTests.exe --additional-seeds
# 위 네 옵션은 exit 0
```

AddressSanitizer를 켠 별도 테스트 빌드도 만들었으나, 실행 직후
`interception_win.cpp:171 / Interception failure`로 도구가 초기화에 실패했다.
테스트 본문이 실행되지 않아 **ASan 메모리 검증 결과는 없음**으로 남긴다.
검사 기능 일부를 끄고 이를 통과로 처리하지 않았다. 빌드는 기존 무시 대상
`build-v1261-test/asan` 안에 있으며 배포 파일에는 포함되지 않는다.

이번에 확인한 결함은 모두 모의 응답 또는 주입한 이벤트 순서에 대한 결과다.
실제 물리 디스플레이 신호 끊김과의 인과관계, 다른 GPU/드라이버에서의 재현 여부,
전체 입력 지연과 장시간 실기 동작은 여전히 미확인이다. 수정 및 배포는 하지 않았다.
